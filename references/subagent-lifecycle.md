# Sub-agent Lifecycle

Covers one-off delegation. For a real fan-out — more than a couple of sub-agents genuinely in flight at once — see `multi-agent-hierarchy.md` for role clarity, task routing, and shared-worktree safety on top of everything below.

**When to spawn.** Default to delegating — including big, self-contained chunks of work, not just narrow single-purpose tasks. Spawn a sub-agent when: (a) it can run in parallel with other independent work, (b) doing it inline would fill your own context with detail nobody downstream needs (full file contents explored, draft iterations, raw search output), or (c) it's simply a large piece of implementation or research on its own — a whole subtask, a full file's worth of changes, an entire investigation — even with nothing else running in parallel. Size alone is a reason *to* delegate, not a reason to keep it close: bigger tasks generate more context to pollute you with, not less. Skip delegation only for what's genuinely answerable in one or two direct tool calls.

**Concurrency cap on ad hoc fan-out.** Don't spawn an unbounded number of sub-agents in one batch just because a task decomposes into that many independent pieces — pick a concurrency cap appropriate to your harness (check its actual limits/guidance rather than assuming) and run the rest in waves, starting the next wave as slots free up, rather than firing everything in one message. This is specifically about your own direct sub-agent calls — a deterministic `Workflow`-style tool (`workflows-and-pacing.md`) manages its own internal concurrency separately and isn't bound by this. If a task would genuinely need more parallelism than a sane ad hoc cap allows, that's itself a signal to reach for a `Workflow`-style tool instead of hand-spawning many waves yourself.

**Mid-task scope creep.** When new instructions land while work is already in flight — a new constraint, an edge case, a related fix — resist doing it inline just because delegating the addendum feels like more overhead. Re-brief the existing sub-agent if it's still addressable, or spawn a new one scoped to the addition, the same way the original task was delegated. Handling it inline is only correct if it would have been a 1–2-call task on its own, independent of what's already running.

**Rotation for long-running sub-agents.** A sub-agent's own context degrades the same way yours does — a long run in one continuous sub-agent session accumulates draft iterations, dead ends, and re-reads until its judgment gets worse, not better. For any sub-agent task large enough to span multiple real milestones, checkpoint at each milestone into a persistent handoff artifact (a subtask file's Implementation Notes, or a scratch file for non-tracked work), then rotate: spawn a fresh sub-agent to continue from that checkpoint instead of piling the next milestone onto the same one. You decide when to rotate — a natural milestone boundary, or visible drift/repetition in a sub-agent's output — and always brief the new sub-agent from the written handoff artifact, never "continue where the last one left off" with nothing written down.

**Briefing.** A sub-agent starts with zero conversation history. Hand it everything it needs up front: exact file paths, the specific question, relevant constraints from the project's docs/config, and what shape the answer should take. Never write "based on what we discussed" — the sub-agent didn't see it.

**Nesting.** Sub-agents execute; they don't spawn further sub-agents on their own initiative. Default to one level (you → sub-agent) so the fan-out stays predictable and auditable — a sub-agent may spawn its own child only when your brief explicitly authorizes that lead role for a genuinely multi-part workstream (see `multi-agent-hierarchy.md`'s role hierarchy for when that's justified and how to keep it safe). Deeper, deterministic multi-stage fan-out (parallel/pipeline stages, adversarial verification panels) is a distinct, heavier tool that needs explicit user opt-in — see `workflows-and-pacing.md`. Proposing it, however, is something you should do proactively once a task looks workflow-shaped.

**Who manages a sub-agent.** Whichever agent spawned it. That agent reads the result, validates it before trusting it — a sub-agent's summary describes what it *intended* to do, not necessarily what it did; check actual diffs/output, don't just relay the summary — integrates it, and decides any follow-up. Sub-agents never talk to the user directly and are never left orphaned — if a background sub-agent's result won't be used, still note that it finished rather than silently dropping it.

**Where results live.**

- **Ephemeral (the default):** a sub-agent's reasoning/tool-call trace stays in its own transcript; it doesn't need to be copied anywhere. Keep only what you need from the result — a summary, a diff, a decision — not the sub-agent's full working.
- **Durable deliverables** (a design, an architecture decision, a plan worth resuming later): synthesize the sub-agent's output into a proper artifact and file it where the project's task-intake system already expects it — see `task-intake-and-tracking.md`. Don't paste a raw sub-agent transcript in as "the plan" — write the plan.
- **Code changes:** land as diffs/commits in the repo. That's the durable record; no separate log needed.
- **Review/audit findings:** surface to the user directly. If a finding should be remembered long-term, it goes into the relevant project reference doc or agent-instructions file per `continuous-documentation.md` — not into a new ad hoc workflow-tracking log.

There should be no separate "sub-agent activity log" by design — durable output belongs with the thing it's about (the plan, the code, the reference doc), not in a workflow-tracking archive that goes stale.
